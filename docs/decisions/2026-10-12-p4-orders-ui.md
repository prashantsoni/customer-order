## Status

Accepted. Confirm dialog added on owner decision. Other choices remain inferred; builder to confirm.

## Context

Phase P4 builds the order UI: the order form, the order detail page with lines and status actions, the order list with filters, and the orders section on the customer detail page. The documents fix the behaviour (PRD FR-06 to FR-12, FR-16) but not the layout or the confirmation rules for each action ([PRD](../requirements/refined/customer-order-prd.md), [implementation plan P4](../plan/implementation-plan.md)).

## Options Considered

| Topic | Chosen | Alternative | Trade-offs |
|-------|--------|-------------|------------|
| New order form | Customer select and first line on one form; saves as Draft | Customer first, then a separate line step | One form and one save. A Draft always has at least one line ([D-14](2026-10-11-minimum-one-line-per-order.md)). |
| Line editing | Inline line form on the Draft detail page; the same form adds and edits (Add line or Save line) | Line edit in a dialog | No second dialog to manage. Lines stay visible while editing. |
| Last line | Remove is disabled on the last line; the domain also blocks it | Remove, then show an error | The control states the rule up front. The domain check remains the source of truth. |
| Confirm order | Confirmation dialog (native `<dialog>`, same as Cancel and Delete) | No dialog | One extra click. Confirm is one way ([D-03](2026-10-11-order-status-one-way.md)), so a slip cannot be undone. The PRD does not require the dialog; see Assumptions. |
| Cancel and Delete | Native `<dialog>` with Cancel first; Delete is for Drafts only ([D-07](2026-10-11-order-delete-and-cancel-rule.md)) | Immediate action | Prevents accidental loss and matches [D-32](2026-10-12-p3-ui-approach.md). |
| Price entry | Unit price typed as decimal text; `parseLineText` in the domain parses it to cents | Parse in the view | The UI never parses money ([D-04](2026-10-11-money-integer-cents.md)). |
| List filters | Status select and customer-name search, combined through the domain `filterOrders` | Separate filter results | One rule set in the domain. The empty state and the no-results state are separate messages. |
| Customer orders | Table on the customer detail page replaces the P3 placeholder (FR-11) | Keep the placeholder | Meets FR-11. Links go to the order detail page. |

## Decision

Use one order form (customer and first line), inline line editing on Draft orders with Remove disabled on the last line, dialogs for Confirm, Cancel and Delete, unit price parsed by the domain, a combined status and customer search filter through `filterOrders`, and an order table on the customer detail page.

## Reason

These choices follow the plan's P4 task list, keep totals, validation, search and filter in the domain, and keep the number of dialogs small ([D-21](2026-10-11-vanilla-js-no-build-step.md), [D-24](2026-10-11-text-rendering-textcontent.md)).

## Consequences

* The order total is read from `orderTotalCents` at render time and never stored ([D-11](2026-10-11-derived-order-total.md)).
* Confirmed and Cancelled orders are read-only. Their lines show no edit or remove controls.
* A failed save keeps the entered line values ([D-18](2026-10-11-save-failure-handling.md)).
* Deleting a customer with orders states the order count ([D-06](2026-10-11-customer-deletion-cascade.md)).

## Assumptions and Risks

* Decided: Confirm asks for confirmation because it cannot be undone. The PRD names confirmation for line removal, Delete and Cancel, so the Confirm dialog goes beyond the written requirement.
* Risk: a Draft confirmed by mistake is reduced by the dialog. Cancelling the dialog leaves the Draft unchanged (e2e test "keeps a Draft when Confirm order is cancelled in the dialog").
